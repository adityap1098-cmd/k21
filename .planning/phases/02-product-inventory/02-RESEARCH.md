## User Constraints (from CONTEXT.md)

### Locked Decisions

**Variant model:**
- Flexible JSONB attributes — `product_variants` table with `attributes JSONB` column: `{"size": "M", "color": "Red"}`
- Every product always has at least one variant — products with no size/color get an auto-created default variant with `attributes: {}`
- `inventory_movement` always references a `variant_id`, never a `product_id` directly
- Each variant has independent selling price (`price` column on `product_variants`) — not a base-price delta
- Each variant has cost price (`cost_price` column on `product_variants`)

**SKU & barcode ownership:**
- SKU and barcode both live on `product_variants` — the parent product has no SKU
- `sku` is required and unique across all variants
- `barcode` is optional (nullable)
- Default variant SKU is auto-generated by the system (slug from product name + short ID) — staff can edit after creation

**Category structure:**
- Two-level hierarchy: parent category → child category
- `categories` table with `parent_id` (nullable FK to self) — max one level of nesting enforced at application layer
- Each product belongs to exactly one category (`category_id` FK on `products` table)
- Category management restricted to Admin and Owner roles only

**Low-stock alert delivery:**
- Write a record to a `notifications` table (user_id, type, payload, read_at) + enqueue a BullMQ job that creates the notification records
- `low_stock_threshold` configured per variant (nullable — null means no alert for that variant)
- Notifications sent to all users with Owner or Admin role

**Inventory movement design:**
- Append-only (non-negotiable) — no UPDATE or DELETE on `inventory_movements`
- Corrections go through ADJUSTMENT movement type (with required reason + approver per INV-04)
- Concurrent stock decrements use `SELECT ... FOR UPDATE` in a single PostgreSQL transaction (INV-05)
- Stock reservation: a `stock_reservations` table holds reserved qty for confirmed-but-not-shipped orders

- BullMQ job implementation for low-stock alert dispatch
- Stock opname workflow UX (batch input vs. line-by-line)

## Summary

Phase 2 builds the data foundation for the entire ERP. The core challenge is correctness under concurrency: two simultaneous POS sales must not both succeed when only one unit remains. The solution is locked in — `SELECT ... FOR UPDATE` inside a Drizzle-managed PostgreSQL transaction — and the project's existing stack (postgres.js with `prepare: false` for PgBouncer TRANSACTION mode) supports this pattern cleanly.

The schema design uses JSONB attributes on `product_variants` for flexible option handling, an append-only `inventory_movements` table as the immutable audit trail, and a `stock_reservations` table for hold logic. Redis (via ioredis, already in package.json) serves as the real-time stock cache so read-heavy POS lookups don't hit Postgres on every barcode scan. BullMQ (also already installed at v5) handles asynchronous low-stock alert dispatch.

All four external dependencies required for this phase (drizzle-orm, ioredis, bullmq, zod) are already in `apps/api/package.json`. No new packages need to be installed. The module structure follows the established pattern from Phase 1: `modules/{domain}/{domain}.service.ts` + `{domain}.router.ts` + `{domain}.test.ts` + `index.ts`. The only new structural element is the Drizzle migration for five new tables.

**Primary recommendation:** Build in this order: schema → migrations → categories module → products module → inventory module (movements + reservations + opname + low-stock alerts). Each layer depends on the previous. The inventory module is the largest and should be split into sub-services (movement.service, reservation.service, opname.service, lowstock.service) to stay under the 800-line file limit.

### Pattern 1: Drizzle Transaction with SELECT FOR UPDATE
**What:** Stock decrement inside a Postgres transaction with row-level locking to prevent oversell.
**When to use:** Every time available stock is decremented (SALE, TRANSFER out, reservation creation).
**Example:**
```typescript
// Source: Drizzle ORM docs — transactions + postgres.js
import { db } from '../../db/index.js'
import { sql } from 'drizzle-orm'

export async function decrementStock(params: {
  variantId: string
  qty: number
  movementType: 'SALE' | 'TRANSFER' | 'RETURN' | 'PURCHASE' | 'ADJUSTMENT'
  reference: string
  performedBy: string
}): Promise<void> {
  const { variantId, qty, movementType, reference, performedBy } = params

  await db.transaction(async (tx) => {
    // Lock the variant row for this transaction
    const rows = await tx.execute(
      sql`SELECT id, stock_qty FROM product_variants WHERE id = ${variantId} FOR UPDATE`
    )
    const variant = rows[0] as { id: string; stock_qty: number }

    if (!variant) throw new Error('VARIANT_NOT_FOUND')

    const available = variant.stock_qty - (await getReservedQty(tx, variantId))
    if (available < qty) throw new Error('INSUFFICIENT_STOCK')

    // Append-only movement record
    await tx.insert(inventoryMovements).values({
      id: randomUUID(),
      variantId,
      movementType,
      qty: movementType === 'SALE' || movementType === 'TRANSFER'
        ? -Math.abs(qty)
        : Math.abs(qty),
      reference,
      performedBy,
      createdAt: new Date(),
    })

    // Update denormalized stock counter
    await tx.execute(
      sql`UPDATE product_variants SET stock_qty = stock_qty - ${qty} WHERE id = ${variantId}`
    )
  })
}
```

### Pattern 3: Redis Cache-Aside for Real-Time Stock
**What:** On read: check Redis first, fallback to Postgres, populate cache. On write: update Postgres first, then update cache.
**When to use:** GET /products/:id/stock and POS barcode lookup.
**Example:**
```typescript
// Source: ioredis docs + cache-aside pattern
import { redis } from '../../queues/redis.js'

const STOCK_KEY = (variantId: string) => `stock:variant:${variantId}`
const STOCK_TTL = 300  // 5 minutes

export async function getStockCached(variantId: string): Promise<number> {
  const cached = await redis.get(STOCK_KEY(variantId))
  if (cached !== null) return parseInt(cached, 10)

  const rows = await db
    .select({ stockQty: productVariants.stockQty })
    .from(productVariants)
    .where(eq(productVariants.id, variantId))
    .limit(1)

  const stock = rows[0]?.stockQty ?? 0
  await redis.setex(STOCK_KEY(variantId), STOCK_TTL, stock.toString())
  return stock
}

// After any stock write: invalidate or update the cache
export async function invalidateStockCache(variantId: string): Promise<void> {
  await redis.del(STOCK_KEY(variantId))
}
```

### Pattern 4: BullMQ Low-Stock Alert Queue
**What:** After a stock decrement, if `stock_qty < low_stock_threshold`, enqueue a job that inserts notification rows for all Owner/Admin users.
**When to use:** End of every successful `decrementStock()` call.
**Example:**
```typescript
// Source: BullMQ v5 docs
import { Queue, Worker } from 'bullmq'
import { redis } from './redis.js'

export const lowStockQueue = new Queue('low-stock-alerts', { connection: redis })

// In movement.service.ts — after successful decrement:
async function checkAndEnqueueLowStock(variantId: string, currentStock: number) {
  const variant = await getVariantThreshold(variantId)
  if (variant.lowStockThreshold !== null && currentStock <= variant.lowStockThreshold) {
    await lowStockQueue.add('check-low-stock', { variantId, currentStock })
  }
}

// Worker (registered at app startup):
export const lowStockWorker = new Worker('low-stock-alerts', async (job) => {
  const { variantId } = job.data
  const admins = await getOwnerAndAdminUsers()
  await db.insert(notifications).values(
    admins.map(user => ({
      id: randomUUID(),
      userId: user.id,
      type: 'LOW_STOCK' as const,
      payload: { variantId, currentStock: job.data.currentStock },
      readAt: null,
      createdAt: new Date(),
    }))
  )
}, { connection: redis })
```

### Pattern 6: Stock Opname with Auto-ADJUSTMENT
**What:** Receive array of `{ variantId, physicalCount }`, compare to current stock, insert ADJUSTMENT movements for discrepancies.
**When to use:** POST /inventory/opname
**Example:**
```typescript
export async function runStockOpname(params: {
  items: Array<{ variantId: string; physicalCount: number }>
  performedBy: string
  ipAddress: string
}): Promise<{ adjustments: number }> {
  const opnameId = randomUUID()
  let adjustmentCount = 0

  await db.transaction(async (tx) => {
    for (const item of params.items) {
      const [variant] = await tx.execute(
        sql`SELECT id, stock_qty FROM product_variants WHERE id = ${item.variantId} FOR UPDATE`
      ) as Array<{ id: string; stock_qty: number }>

      const discrepancy = item.physicalCount - (variant?.stock_qty ?? 0)
      if (discrepancy === 0) continue

      await tx.insert(inventoryMovements).values({
        id: randomUUID(),
        variantId: item.variantId,
        movementType: 'ADJUSTMENT',
        qty: discrepancy,
        reason: `Stock opname ${opnameId}`,
        approvedBy: params.performedBy,
        reference: `OPNAME-${opnameId}`,
        performedBy: params.performedBy,
        createdAt: new Date(),
      })

      await tx.execute(
        sql`UPDATE product_variants SET stock_qty = ${item.physicalCount} WHERE id = ${item.variantId}`
      )
      adjustmentCount++
    }
  })

  return { adjustments: adjustmentCount }
}
```

### Anti-Patterns to Avoid
- **Updating inventory_movements:** Never. Corrections go through ADJUSTMENT movements. The append-only invariant is the core value of the ERP.
- **Stock from summing movements:** Don't compute current stock by `SUM(qty)` on movements at query time — this is O(n) and breaks under POS load. Maintain a denormalized `stock_qty` column on `product_variants` updated in the same transaction as the movement insert.
- **Skipping FOR UPDATE on decrements:** Without the row lock, two concurrent transactions can both read `stock_qty = 1`, both pass the availability check, and both decrement — leaving stock at -1. Always lock the variant row.
- **Separate product/variant code paths:** Never check "does this product have variants?" — every product always has at least one variant. One code path everywhere.
- **Redis as source of truth:** Redis cache can be stale or evicted. Always write to Postgres first, then update/invalidate cache. Postgres is authoritative.
- **Forgetting to invalidate cache after stock update:** After any successful movement commit, immediately call `invalidateStockCache(variantId)` or update the cached value to the new quantity.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Job queue + retry logic | Custom queue with setTimeout | BullMQ (already installed) | BullMQ handles retries, delays, job persistence in Redis, backpressure |
| Slug generation for SKU | Custom string sanitizer | `name.toLowerCase().replace(/[^a-z0-9]+/g, '-')` inline | Simple enough inline; no library needed |
| JSONB schema validation | Custom JS type guards | Zod `.record(z.string())` for attributes | Already using Zod; validates at route boundary |
| Connection management | Custom Redis pool | ioredis (already installed) | ioredis handles reconnect, cluster, pipelining |
| Database transactions | Manual BEGIN/COMMIT | `db.transaction(async (tx) => ...)` in Drizzle | Drizzle handles rollback on throw automatically |

**Key insight:** The hardest correctness problem in this phase (concurrent oversell) is solved by a single PostgreSQL feature (row locking). Don't add distributed locks, optimistic concurrency, or event sourcing — they add complexity without benefit at this scale.

## Common Pitfalls

### Pitfall 1: postgres.js + FOR UPDATE Raw SQL
**What goes wrong:** `db.execute(sql\`SELECT ... FOR UPDATE\`)` outside a transaction acquires a lock that is immediately released because PgBouncer returns the connection to the pool after the statement. The lock has zero duration.
**Why it happens:** PgBouncer TRANSACTION mode — each statement may get a different server connection.
**How to avoid:** Always wrap `SELECT ... FOR UPDATE` inside `db.transaction(async (tx) => { ... })`. Inside the transaction callback, use `tx.execute()` not `db.execute()`.
**Warning signs:** Tests pass (they use a single connection) but production has oversell events.

### Pitfall 2: drizzle-kit with NodeNext ESM
**What goes wrong:** `drizzle-kit generate:pg` fails with `require()` errors when schema files use ESM imports.
**Why it happens:** drizzle-kit v0.20 is CommonJS and uses `require()` to load schema files; NodeNext ESM module resolution resolves `.js` to `.ts` only via tsx/cjs intercept.
**How to avoid:** Use the established workaround already in `package.json`: `node --require tsx/cjs node_modules/drizzle-kit/bin.cjs generate:pg`. This is already set up — just run `pnpm db:generate`.
**Warning signs:** `Error: Cannot use import statement in a module` from drizzle-kit CLI.

### Pitfall 3: JSONB attributes type in TypeScript
**What goes wrong:** Drizzle infers JSONB columns as `unknown` type. Accessing `variant.attributes.size` fails TypeScript checks.
**Why it happens:** Drizzle cannot statically type arbitrary JSONB content.
**How to avoid:** Cast explicitly at point of use: `(variant.attributes as Record<string, string>).size`. Define a type alias `type VariantAttributes = Record<string, string>` in the schema file and use it consistently.
**Warning signs:** TypeScript errors on JSONB field access; `as any` appearing in services.

### Pitfall 4: BullMQ Worker not started
**What goes wrong:** Jobs are enqueued but notifications are never created. No error — jobs just pile up in Redis.
**Why it happens:** A `Queue` enqueues jobs; a `Worker` processes them. They are separate objects. If the Worker is defined but never instantiated at startup, nothing runs.
**How to avoid:** Register the low-stock worker in `apps/api/src/index.ts` startup (or a dedicated `workers/index.ts` imported from `index.ts`). Confirm with a log line on worker init.
**Warning signs:** `low-stock-alerts` queue grows in Redis; no notification rows appear in DB.

### Pitfall 5: Forgetting the default variant on product creation
**What goes wrong:** A product is created with no variants. All downstream inventory operations that call `WHERE variant_id = ?` return nothing. POS cannot find the product by barcode/SKU.
**Why it happens:** Default variant creation is easy to omit in the service.
**How to avoid:** The `createProduct()` service MUST use `db.transaction()` that inserts both the product row and the default variant row atomically. Add a test that asserts `product_variants` count after `createProduct()`.
**Warning signs:** Integration test for product list returns products with 0 variants.

### Pitfall 6: Stock reservation and available stock calculation
**What goes wrong:** `SELECT ... FOR UPDATE` on `product_variants` sees `stock_qty = 5` but 3 units are reserved for pending orders. The service allows 5 more units to be decremented, leaving -3 available.
**Why it happens:** `stock_qty` is total stock, not available stock. Available = `stock_qty - SUM(reserved_qty WHERE status = 'ACTIVE')`.
**How to avoid:** In `decrementStock()`, after locking the variant row, query `stock_reservations` within the same transaction to get total reserved quantity before checking availability.
**Warning signs:** Oversell events on products with active reservations.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Summing movements for current stock | Denormalized `stock_qty` column + movements as audit trail | Standard practice | Read performance: O(1) vs O(n) for stock reads |
| Single product record with option arrays | Separate `product_variants` table with JSONB attributes | Industry standard post-2018 | Enables per-variant pricing, stock, barcode — required for Shopee/TikTok sync |
| Bull (v3) | BullMQ (v5) | 2021 | BullMQ is the maintained successor; completely different API |
| drizzle-orm `for('update')` builder method | `sql\`... FOR UPDATE\`` raw tag inside transaction | Both work in drizzle-orm 0.30 | Use raw SQL form — more explicit, no ambiguity about scope |

**Deprecated/outdated:**
- `bull` (npm): Replaced by `bullmq`. Project already has `bullmq` v5 — do not use `bull`.
- `node-postgres` (`pg`): Project uses `postgres` (postgres.js) — required for PgBouncer. Do not add `pg`.
- `redis` (npm package): Project uses `ioredis` — do not add `redis` package.

## Open Questions

1. **ADJUSTMENT approval flow**
   - What we know: ADJUSTMENT requires `reason` + `approvedBy`. INV-04 is clear.
   - What's unclear: Whether approval is blocking (approver must act before movement is recorded) or recorded-at-time (performer is also the approver for opname). Claude's Discretion.
   - Recommendation: Use recorded-at-time for v1 — the `performedBy` user for opname is the approver. Separate async approval workflow can be added in v2 without schema change (just filter on `approvedBy != performedBy`).

2. **Redis connection for BullMQ vs ioredis cache**
   - What we know: BullMQ requires `maxRetriesPerRequest: null` on the ioredis connection.
   - What's unclear: Whether to share one Redis connection or use two.
   - Recommendation: Use two connections — one for BullMQ (with BullMQ-required options) and one for general cache. BullMQ docs explicitly recommend this because BullMQ keeps the connection in subscriber mode.

3. **Stock opname scope: full vs partial**
   - What we know: INV-08 says "input hitungan fisik" — physical count.
   - What's unclear: Does each opname cover all variants, or can staff submit a partial count (only some variants)?
   - Recommendation: Allow partial — staff submits an array of `{ variantId, physicalCount }`. Only variants submitted are adjusted. This maps naturally to how physical counts work in retail (one shelf at a time).
